# 점검일 자동화 — 감시를 거는 법과, 실패했을 때 보는 순서

몇 달 동안 감시를 고쳐 왔지만 **"새 버전이 뜨면 시작"** 이라는 전제 하나가 틀려서 계속 어긋났다.
2026-10-09 하루에 드러난 실패를 원인별로 적는다. 감시를 새로 걸 때 아래 **규칙**을, 실패를 볼 때 **진단 순서**를 따른다.

## 1. 2026-10-09 에 실제로 난 실패 (전부)

곁가지: 이날 세션 예약(CronCreate)은 VS Code 세션 안에서 돌았다. 세션 예약은 **세션이 켜져 있고 쉬고 있을 때만** 발화한다.
폴러(배경 Bash)는 세션이 다른 일을 해도 계속 돈다 — 실감시는 폴러가, 예약은 안전망이다.

## 2. 감시를 새로 걸 때의 규칙

### 규칙 A — 무엇을 "새 업데이트"로 볼 것인가

- **기준선 = 사이트가 마지막으로 패치 파이프라인을 끝낸 resVersion.** 감시를 거는 순간의 CDN 버전이 아니다.
  지난 점검 작업 폴더의 `baseline.txt`(done 때 갱신됨)나, 그 날짜 커밋의 `.gamedata` 버전을 쓴다.
- 감시를 걸 때 **지금 CDN 버전 ≠ 기준선이면 이미 데이터가 와 있는 것**이다 — 기다리지 말고 곧장 파이프라인을 돌린다
  (중섭은 전날 깔고, 한섭도 작은 패치로 미리 깔 수 있다). 사용자에게 "데이터 이미 들어와 있음"을 먼저 알린다.
- `PRE_SEEDED`(업데이트 전 기준선 재심기)는 **쓰지 않는다.** 등록 뒤 작은 업데이트가 끼어 일찍 깨어나는 건 손해가 작다
  — 파이프라인은 여러 번 돌아도 안전하다. 새 데이터를 기준선으로 삼켜 하루를 날리는 게 훨씬 크다.
- 버전이 그대로여도 **예고 시각이 지나면 한 번은 파이프라인을 돌린다**(예고된 신규 오퍼·이벤트가 데이터에 있는지 직접 확인).
  확인법: `python3 scripts/fetch-gamedata-cdn.py --server cn --tables character_table,activity_table --out <임시>` 로 받아
  예고된 오퍼·이벤트 id 가 들었는지, 그게 `app/data/operators.json`·이벤트 도감에 이미 반영됐는지 대조.

### 규칙 B — 구조

- 실감시는 **배경 폴러**(2분 30초), 예약은 **안전망**(5~15분). 예약만 촘촘히 돌리지 않는다 (기억 `patch-day-watcher`).
- 폴러 마감 시각(`STOP_AFTER`)이 지난 뒤엔 폴러를 다시 띄우지 않게 가드에 적는다 — 띄우면 즉시 꺼져 깨우기를 되풀이한다.
- 파이프라인은 **하위 에이전트**(사용자 지정 2026-10-08: Opus 5.5 · medium, bypass permissions 는 세션 모드를 물려받는다)에게
  절차 파일(`pipeline.md`)을 읽혀 맡긴다 — 긴 세션 맥락을 싣고 돌지 않게. 부모는 결과만 받아 확인·보고·예약 정리.
- 락 먼저(`state.sh lock`) → 하위 에이전트 → 푸시 → 배포 래퍼(`~/.claude/patch-day/deploy-after.sh`) → `state.sh done`.

## 3. CI(data-refresh)가 실패했을 때 진단 순서

```bash
gh run list -L 8                                   # 몇 번째부터 실패인가
gh run view <id> --log-failed | grep -E "Traceback|Error|⚠|✗" | tail -20
```

1. **"CDN 수신이 실패해 클뜯 레포판으로 물러났다"** 가 있나 → 어느 서버·어느 표인지
   (`gh run view <id> --log | grep -E "CDN  resVersion|디코딩 실패|레포 폴백"`).
   - `디코딩 실패` → 스키마 문제. 로컬은 캐시(`scripts/fbs/_cache/`) 때문에 멀쩡할 수 있다 — **캐시 없이** 재현:
     스크립트를 임시 폴더로 복사해 `_cache` 없이 `fetch-gamedata-cdn.py --server <s> --tables <표>` 를 돌린다.
     (`rm -rf` 는 승인 프롬프트에 걸린다 — 지우지 말고 새 폴더에 복사할 것)
   - 고정본으로도 안 읽히면 그 서버가 새 구조로 올라간 것 → `python3 scripts/fbs-repair.py <표> --server <s>`,
     맞게 되면 `fetch-gamedata-cdn.py --server <s> --pin-schemas` 로 고정본 갱신 후 커밋.
2. **Traceback** 이 빌더에서 났나 → 레포 폴백 데이터의 숫자 열거값(#5)부터 의심.
3. 1단계(오퍼 도감)만 커밋되고 2단계에서 죽었으면 — 사이트엔 반쯤 갱신된 데이터가 **커밋만 되고 배포는 안 된** 상태다.
   고친 뒤 `gh workflow run data-refresh` 로 한 바퀴 돌리거나, 점검 파이프라인을 돌려 배포한다.
4. 고친 스크립트는 **푸시해야 CI 가 쓴다** (CI 는 origin/main 을 체크아웃). 배포는 필요 없다 — 다음 CI 가 배포한다.

## 4. 관련 파일

- `scripts/fetch-gamedata-cdn.py` — `schema_candidates`·`decode_any`(손본 것 → 캐시 공개본 → 갓 받은 공개본 → 고정본), 종료 코드 0/1/3, `--pin-schemas`
- `scripts/fbs/pinned/` — 고정 스키마 (2026-10-09, 한섭·글섭·일섭이 읽히던 판) · `scripts/fbs/<서버>/` — 손본 서버 전용 스키마
- `scripts/cdntables.py` — 빌더들이 표를 직접 받을 때도 `decode_any` 를 쓴다
- `scripts/ci-refresh.sh` — fetch-cdn 종료 코드 3 처리
- `.ci/resversion.json` — CI 감시(`ci-probe-version.mjs`)가 본 버전. **사람 파이프라인이 처리한 버전과는 다르다**
- `~/.claude/scheduled-tasks/<작업>/` — 감시 작업 판 (`check.sh`·`watch.sh`·`state.sh`·`pipeline.md`)
